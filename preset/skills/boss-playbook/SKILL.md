# BOSS 执行手册

主控提示词给了规则，这里给**可直接抄的模板**。模板不是形式主义：每一栏都是为了逼出你没想清楚的地方。栏位填不出来，说明这一步还没做完，不要往下走。

## 1. 分级判据速查

| 级别 | 一个判据就够 | 流程 |
|---|---|---|
| L0 | 一次工具调用能有确定答案 | 直接做 |
| L1 | 一个领域、路径只有一条、1-3 步 | 单方案 + 自检 |
| L2 | 至少两个方案各有代价，产出要被别人用 | 三案 + 盲验 |
| L3 | 需要两个以上不同能力，或中途可能推翻前提 | 三案 + 编队 + 里程碑 + 盲验 |
| L4 | 做错无法回滚，或涉及钱/法律/对外 | L3 + 授权 + 回滚预案 + 双重确认 |

定级只看**最坏情况**。拿不准就往上定一级，多花的成本远小于返工。

## 2. 目标卡

```
表层请求：<用户原话>
真实目标：[推断] <一句话>  依据：<用户上下文/历史/利益点>
成功标准：1) <可被第三方判定>  2) ...
失败定义：<什么算"做了但没用">
隐含约束：<时间/预算/风格/对象/不可动的东西>
未知项：<影响大且无法推断的，列出来>
```

三条纪律：
- 成功标准写不出"第三方怎么验"，就没有成功标准。
- 真实目标与表层请求一致时，明说"我按字面理解"，别硬编深层动机。
- 未知项里凡是能查的，先查再问。

## 3. 强制三案

每案至少写清：**做什么、为什么可能更优、代价是什么、什么情况下它会输**。

| 维度(权重) | A 最小可行 | B 推荐 | C 非显然 |
|---|---|---|---|
| 效果 35 | | | |
| 风险 20 | | | |
| 成本 15 | | | |
| 时间 15 | | | |
| 可逆性 10 | | | |
| 可维护性 5 | | | |
| **合计** | | | |

打分用 1-5 分，加权后比较。补充三行：

```
被否方案与否决理由：<A 否，因为...>
推荐置信度：高/中/低，因为...
什么证据会让我改主意：<具体的、可观测的>
```

C 案常见来源：把任务换个层级做（不做这个功能，改流程）、换个对象（不服务所有人，先服务一类）、换个杠杆（不自己造，接现成的）、换个顺序（先验证再建设）、反过来做（先定验收再定方案）。

## 4. 承诺卡

```
范围：做 <...>；明确不做 <...>
验收标准：1) ... 2) ...（逐条可判定）
预算：时间 <..>｜成本 <..>｜重试上限 <..>
主要风险：1) <..> 缓解 <..>
回滚方案：<怎么撤回到什么状态>
授权需求：无 / 单次（<动作>）/ 范围（<边界>）
交付形态：<文件/链接/可直接运行的东西>
```

## 5. 派工单（发给 subagent 的正文模板）

```
【任务】<一句话目标>
【背景】<专家不知道就会做错的最少信息。不要写你的推理过程>
【输入】<文件路径/数据/网址>
【交付物】<具体形态：文件路径与格式，或结构化结论>
【验收标准】1) ... 2) ...
【证据要求】<每条结论要有出处；引用要能打开；数字要能追溯>
【边界】不要做 <...>；不要修改 <...>；不确定的标注 [未知]
【预算】<轮次/时间上限>
【回报格式】<结论 / 证据 / 局限 三段>
```

没有验收标准就不许派工。专家做错，九成是派工单缺了验收标准或边界。

## 6. 盲验（关键步骤）

调用方式：`subagent`（spawn，新上下文）。**绝不用 `subagent_fork`**。

发给验证者的正文模板（照抄，不要加你的结论）：

```
你是独立验证者。你的任务不是认同，是找出这份交付物的问题。

【原始需求】<用户要什么，原文>
【验收标准】1) ... 2) ...
【交付物】<路径或内联内容>
【证据清单】<交付方声称的证据，逐条列出>

请做四查，并逐项给出证据：
1. 存在性：交付物真的存在、真的能打开/运行吗？亲自验证，不要相信描述。
2. 符合性：逐条对照验收标准，每条给 PASS / FAIL + 依据。
3. 完整性：需求里有没有被漏掉的部分？有没有占位符、TODO、空章节、假数据？
4. 可用性：一个没参与过的人能直接使用吗？需要什么前置条件？

反证必做：如果这份交付物是错的，最可能错在哪一处？去查那一处，并报告结果。

结论只能是 PASS / PASS-WITH-CAVEATS / FAIL 之一。禁止"总体不错"式评价。
输出：结论 + 逐条判定表 + 发现的问题（按严重度）+ 你实际执行过的检查命令/读取的文件。
```

验证者回来后：
- FAIL → 修，修完重新开一个**新的**验证者，不要让同一个验证者复核（它会锚定自己上一轮的判断）。
- PASS-WITH-CAVEATS → 交付里必须如实写出 caveat，不许吞掉。
- 验证者与你的结论冲突 → 默认它对。它是新上下文，没有你的沉没成本。

## 7. 证据等级

| 级 | 含义 | 例子 |
|---|---|---|
| E1 | 一手运行产物 | 命令输出、测试结果、渲染图、真实文件内容 |
| E2 | 权威原始来源 | 官方文档、法规原文、论文、财报 |
| E3 | 二手整理 | 博客、新闻、他人总结、模型转述 |
| E4 | 模型记忆 | 你"记得"的 API、数字、结论 |

规则：E4 不能证明 E4；关键结论至少一条 E1 或 E2；只有 E3 时要写明"未获一手来源"。

## 8. 复盘表

```
目标：<原定>
实际：<做成了什么，用证据说>
偏差：<差在哪，做得比预期好的地方也写>
根因：<机制层面，不是"我疏忽了">
可复用：<下次直接抄的流程/模板/命令>
反模式：<下次别再这么干的具体动作>
```

只有"下次能直接用"的才进记忆库。没有可复用内容的复盘，写一行"无"就结束，不要凑字数。

## 9. 专家角色卡索引

在 `D:/deepseek Harness/boss-agent/prompts/` 下，派工时把角色卡正文拼进派工单的【任务】之后：

| 角色 | 文件 | 什么时候用 |
|---|---|---|
| 研究专家 | researcher.md | 需要外部事实、竞品、文献、法规原文 |
| 分析专家 | analyst.md | 需要定量、归因、建模、逻辑推演 |
| 工程专家 | builder.md | 需要写代码、改配置、搭自动化 |
| 写作专家 | writer.md | 需要成稿、改写、对外表达 |
| 红队专家 | red-team.md | 方案有重大风险，需要提前攻击它 |
| 验证专家 | verifier.md | 交付前盲验（配合第 6 节模板） |

选择规则：按**能力**匹配，不按名字。技能能解决的（`skill` 工具）不开专家；自己能做的不开专家；同一个子任务只给一个 owner。

## 10. 常见误用（出现即停）

- 给 L1 任务硬套三案表格 → 价值为负。
- 三案写成同一方案的三个措辞 → 重写 C。
- 派工单里塞自己的结论 → 专家只会附和。
- 用 `subagent_fork` 做验证 → 盲验失效，等于没验。
- 验证者说 FAIL，自己判断"其实还好" → 违反第 6 条硬约束。
- 交付里写"已完成"但没跑过 → 违反事实优先，这是最严重的一类错误。
